**Part 1 — B21 wire amendment (do this first, one commit).**
`PreparationFlightStateV1` (`crates/bridge-core/src/preparation_flight.rs:115`)
has `Open {} / BarrierSynced {} / Transferred { reason } / Failed { cause }`
and no success-settlement state. Resolution (dispatch-brief ruling): add
**`Settled {}`** (serde tag `"settled"`) as the success terminal.
`Transferred` remains exclusively the recovery-transfer escape (bound expiry
hands the exact preparation guard to the recovery flight); success must never
be expressed through `Transferred` — consumers may never need free-text
`reason` to distinguish success from recovery. Amendment protocol: update the
A2 golden/serialization tests DELIBERATELY in the same commit (they are the
tripwire, not an obstacle), keep every match on the enum exhaustive without
wildcards, and add the `Settled` round-trip + refusal-shape coverage matching
the existing variants' test idiom. The type is inactive today (zero
production writers/readers) so this is a pure additive variant, not a
migration.

**Part 2 — the claimed, non-cancellable materialization flight (first
production writer).** Wrap the worktree materialization path
(`crates/bridge-worktree/src/backend.rs:2327` `materialize_under_custody`;
the custody entry edge in `crates/bridge-worktree/src/custody.rs`) in a
preparation flight that:

- Is CLAIMED before the first filesystem effect and durably records
  `Open` → (progress) → terminal. The success path terminalizes `Settled`;
  a typed pre-effect failure terminalizes `Failed { cause }`; ownership
  handoff to recovery (T2/T3 wire the expiry path — you must leave
  `Transferred` reachable-by-API but produce NO production caller of it).
- Is NON-CANCELLABLE: the runner retains the map/provider/custodian `Arc`s
  across caller-future drop — dropping the caller's future must not abort a
  claimed flight mid-materialization; the flight runs to its own terminal
  and its durable state reflects the truth of what happened.
- Arms ZERO production timers/deadlines. `PreparationClockV1`
  (`preparation_flight.rs:127`) may be threaded/injected, but nothing in
  production schedules or expires anything — slice 4 owns arming. No
  deadline, no watchdog, no spawn of timing tasks.
- Must NOT call or reintroduce `cleanup_failed_add`
  (`crates/bridge-worktree/src/host_git.rs:44`) on any V3/flight path: a
  partial `git worktree add` under the flight becomes a preserved/protective
  durable state, never repaired by deletion.
- Gains NO new edge in the frozen custody transition table
  (`crates/bridge-worktree/src/custody.rs`); the flight is an OWNER, never
  an outcome authority — context-free callers still never arm `Preserve`.

**Part 3 — M13 phase-distinguished cancellation tests (red-first).** One
test per phase, each dropping/cancelling the caller future at that exact
phase and asserting the expected durable flight state plus the custody
record's state:

1. before-claim — no flight record exists; no filesystem effect.
2. after-claim-before-add — flight reaches its own terminal; no
   `git worktree add` effect admitted.
3. mid-add — the flight completes or preserves protectively; never a
   deletion repair.
4. after-add-before-evidence — durable state truthful about materialization
   having happened; no evidence fabrication.
5. terminal-publication-failure — a failing terminal write is loud/typed,
   never silently swallowed (use a cfg(test) fault seam in the established
   lane idiom).

Each test must be shown red-first: written against the pre-change behavior
(or with the single named mutation that makes it fail) and the evidence
recorded in your handoff.
