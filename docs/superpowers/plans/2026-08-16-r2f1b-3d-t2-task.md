# R2f1b 3d — T2: finite preparation ownership — nonreturning custody sync transfers the pre-effect owner

## Description

Second of three sequential 3d tasks. Base: `main` (post-T1 merge — the tree
already contains `PreparationFlightStateV1::Settled`, the claimed
materialization flight in `crates/bridge-worktree/src/backend.rs`, its
caller-departure sample, the committed-flight cleanup join, and the
backend-owned completion-debt record; read them first and build on them, do
not rework them). Authority: slice-3 brief §3d(b) (M3, on main) and the
focused-boundary design §2.5 (restated below; you need no other document).

**The contract.** Every potentially blocking preparation operation runs
under a 30-second internal action bound and a 31-second observable control
bound (D11). When the bound expires BEFORE the prepared barrier, that is a
typed pre-effect refusal, not workflow cancellation: it admits zero
provider/session/process or `git worktree add` effects and **transfers the
exact preparation guard to the recovery flight rather than dropping it** —
the flight's durable record terminalizes
`Transferred { reason: BoundedPreparationTransferReasonV1 }` (this task
lands the FIRST producer of `Transferred`). The attempt can therefore
terminalize within its admission envelope even while an OS filesystem
operation remains recovery-owned.

**What T2 delivers:**

1. **Clock-observed bounds on the flight's blocking pre-barrier
   operations.** Thread the already-landed `PreparationClockV1`
   (`crates/bridge-core/src/preparation_flight.rs:127`, injectable
   monotonic clock) through the materialization preparation flight. The
   runner observes elapsed time at its blocking pre-barrier operations
   (journal open/publish/sync, custody entry, identity capture — enumerate
   the actual population from the T1 code and list it in your handoff).
   **ZERO production arming:** production constructs the flight with no
   bound armed (slice 4 owns arming) — expiry is only reachable when a
   bound is explicitly injected. No timers, no spawned watchers, no
   `tokio::time` in production paths: the bound check samples the injected
   clock at operation boundaries, exactly like T1's one-sample departure
   check.
2. **The transfer mechanism.** On an observed expiry before the barrier:
   no further effect is admitted; the durable record terminalizes
   `Transferred { reason }` (reason = which operation exceeded which bound,
   through the existing redacting constructor); the guard/ownership moves to
   a recovery-owned handle rather than being dropped — the backend retains
   it the same way the T1 completion-debt record is retained (recovery/
   retirement can inventory it; T3 wires the recovery consumer, so T2 must
   leave a typed, inventoriable handle with NO production consumer yet).
   A nonreturning operation itself cannot be killed — the transfer happens
   at the observing boundary while the stuck operation's future remains
   owned by the transferred handle (never detached-and-forgotten, never
   `cleanup_failed_add`).
3. **The mandated test battery (red-first, each with recorded evidence):**
   - `nonreturning_custody_sync_transfers_pre_effect_owner` — the named
     exit-gate row: a custody sync that never returns, under a manual
     clock advanced past the bound, yields durable `Transferred`, zero
     add/provider effects, and an inventoriable recovery handle holding
     the exact preparation guard.
   - Expiry at each enumerated pre-barrier operation boundary (table test
     or per-op tests — your call, disclosed).
   - A control: the same schedule with the clock NOT advanced completes
     `Settled` normally.
   - A post-barrier control: expiry observed only after the barrier does
     NOT transfer (the flight is committed; phase-3 semantics from T1
     unchanged).
   - Production-default control: with no bound armed, a slow operation
     never transfers (proves zero production arming).

**Binding constraints:** production changes confined to
`crates/bridge-worktree/src/backend.rs` (+ minimal
`crates/bridge-core/src/preparation_flight.rs` additions ONLY if a typed
reason/bound carrier is missing — no changes to the enum's variants or wire
shape); no production timers or arming; no custody-table edge; T1's
departure sample, cleanup join, and completion-debt mechanisms unchanged;
no `rustfmt::skip`; `Cargo.lock` untouched. Caps soft 500 / hard 800
changed lines; STOP and report rather than blow the cap. fmt + workspace
clippy `-D warnings` + workspace suite green on the final head.

**Known environment reds (ledgered, not yours):** in-container whole-bin
`api_entry_resolves_and_serves_through_registry` (flock-EBADF class,
host-green); in-container cargo may hit the egress lock for uncached deps —
record predicted red mutations for host rerun if so, as T1 did.

## Acceptance Criteria

1. `Transferred { reason }` gains its first producer, reachable ONLY via an
   injected/advanced clock bound before the barrier; production default
   arms nothing (control test proves it).
2. The transferred guard is a typed, backend-inventoriable handle that owns
   the stuck operation's future; nothing is dropped, detached-forgotten, or
   deletion-repaired.
3. The named exit-gate test plus the per-operation expiry battery, the
   not-expired control, the post-barrier control, and the
   production-default control are present with red-first evidence per test
   (base-red or named mutation + predicted failing assertion).
4. T1 mechanisms untouched (departure sample, cleanup join, completion
   debt); no wire-shape change; caps respected.
5. fmt/clippy/workspace suite green on the final head; handoff lists the
   enumerated blocking-operation population, per-test red evidence, and any
   design decision inside the frozen contracts.
