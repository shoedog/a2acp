## Findings

**S1 — SMELL — `combine()` ranks `Preserved` above `Retained`, so an outer preservation erases inner retention; the handoff's stated justification for the order is false.**
`crates/bridge-core/src/ports.rs:317-327` (`BackendCleanupDispositionV1::combine`), consumed at `crates/bridge-worktree/src/backend.rs:690-702` (`CleanupReportV1::settled`). Handoff §1 says "an outer preservation cannot erase inner retention" — but `(Preserved, Retained) → Preserved` by construction, and the test that pins it is literally named `outer_preserved_and_inner_retained_do_not_collapse_or_double_signal` (`backend.rs:7143-7151`) while asserting the collapse. What survives is only "not `Complete`", not the retention itself. The two halves describe *different resources* (outer = checkout, inner = backend session/process), so any single scalar loses information; the choice is defensible, but the ordering is the wrong way round against 2c1/2c2 semantics, where `Preserved` is a **settled terminal** custody state and `Retained` is an **unsettled pending obligation** — the unsettled one is what an operator or reaper needs to see. No wrong output today because no production inner backend returns non-`Complete` (`AcpBackend` maps everything to `Complete`, `acp_backend.rs:7189-7229/7320-7381`). This is the one to fix before 3c1: once `ContainerRwBackend` can report `Retained` for a container it failed to reap, a terminal row reading `preserved` will hide a leaked container — and this slice is the only trait pass, so widening the surface later is expensive. Ledger for 3c1: either invert to `Retained > Preserved` or carry inner and outer as two fields.

**S2 — SMELL — the inner-disposition accumulator is cell-scoped, and the cell is evicted on the first `Ok` report, so a later flight can report `Complete` after an earlier one reported `Retained`.**
`crates/bridge-worktree/src/backend.rs:733-740` (`CleanupCellState.inner_disposition`, `#[derive(Default)]` → `Complete`), accumulated at `:1887-1899`. Within one cell the logic is sound: a *skipped* inner (`inner_strength >= strength`) carries the accumulated value forward, and a *refused* inner produces `Err` (`:1897`), so the `Complete` default can never mask a protective result on either path — the specific hazard in the brief does not fire. The gap is across cell lifetime: 2c2 deliberately added durable re-derivation for the **checkout** half precisely because the cell is evicted (`:1867-1877`), and the **inner** half has no equivalent, so it silently restarts at `Complete`. Latent for the same reason as S1.

**S3 — SMELL — `WarmCompletionAction::Cancel` discards a real cleanup's disposition and projects `Complete`.**
`crates/bridge-coordinator/src/dispatch.rs:276-289` and `:353-360` map the `Cancel` arm to `Complete`/`Failed` only; upstream, `crates/bridge-coordinator/src/session_manager.rs:1791-1797` collapses `(Ok(()), Ok(disposition)) → Ok(())` even when the branch at `:1755-1780` created an `ExpiryClaim` and ran a real backend release. I initially traced this as WRONG — workflow-owned warm turn, `Canceled` exit, `expire_after_reconcile` set by a concurrent release landing on a claimed handle (`session_manager.rs:1546`, `:1686`), worktree gate refuses deletion for the context-free entry and returns `Retained` (`backend.rs:2092-2105`) → terminal row says `complete`. It is **not** reachable in production: the only `Cancel`-arm producer is `WarmCompletionGuard::workflow_owner`, whose sole non-test call site (`crates/bridge-a2a-inbound/src/server.rs:854`) sits inside a `#[cfg(test)]` region (`server.rs:867`, `:872`, `:896`); production uses `finish_owner` only (`server.rs:722`, `coordinator.rs:1200`). Reporting the weaker claim: latent, and it becomes real the moment `workflow_owner` is promoted to production.

**S4 — SMELL — `server.rs` updated one terminal projection and left its sibling hardcoded.**
`crates/bridge-a2a-inbound/src/server.rs:4000-4004` still reads `if cleanup_result.is_ok() { "complete" } else { "failed" }`, while the fan-out sibling at `:4285` was changed to `disposition.as_str()` and the coordinator equivalent at `coordinator.rs:1394-1400` was too. Safe today, and I proved it rather than assumed it: the site is reached only after `warm.observe_exit(WarmCompletionExit::Normal)` at `:3998` with no collected error, so `action == Finish`, whose `complete()` returns `Ok(Complete)` unconditionally (`dispatch.rs:346-353`). It is a mislabel waiting on any change to the exit mapping, in a function where the correct pattern is 285 lines away.

**S5 — SMELL — all four registry funnel call sites discard the refusal, so "we did not retire this backend" is unobservable.**
`crates/bridge-registry/src/registry.rs:490`, `:521`, `:532`, `:564`, all `let _ = Self::retire_join_or_refuse(...)`. The `let _ =` predates the slice, but its *meaning* changed: previously it discarded an error from work that happened, now it can discard a decision that the work would not happen. On the two detached drain tasks (`:521`, `:532`, `:564`) there is no caller left to notice. Accepted for 3b2 as the brief allows, but ledger it: a refusal on a drain path deserves a `tracing::warn!` at minimum, and 3c/slice 4 should decide whether an unexposed backend reaching a drain is itself an invariant violation worth journaling.

**S6 — SMELL — two ResilientWarm protective-behavior deltas, both unreachable today.**
(a) `crates/bridge-controller/src/resilient.rs:206` makes the rebuild-configure-failure retire conditional where it was unconditional — an unexposed rebuilt backend now leaks instead of being retired. Practically unreachable: reaching `:204` requires the *original* backend to have exposed at `:172`, and `rebuild()` returns the same backend type. (b) `:172-175` returns `false` on refusal, disabling warm respawn entirely for an unexposed backend, where V2 would have retired/reset/rebuilt. Both are correct fail-closed choices; I flag them only because (a) trades a leak for safety in a direction the rest of the slice trades the other way. V2 byte-identity for the `LegacyV2` path is confirmed: `:183-209` is unchanged from base apart from the guard at `:206`.

**S7 — SMELL — the `ReplayBackend` refusal changes test-composition semantics with no test asserting the new shape.**
`crates/bridge-acp/src/replay.rs:88-97` refuses both methods. `ReplayBackend` is never wrapped in production (the factory wraps only the `AgentKind::Acp` arm, `bin/a2a-bridge/src/main.rs:1584`), so invariant 5(a) has no production exposure — but `ReplayBackend` *is* driven through a real `InboundServer` + `SessionManager` in `bin/a2a-bridge/tests/integration_inbound_kiro.rs:59` and `integration_fanout.rs`. Any of those that takes a gated cleanup path now gets `ResourceFlightUnsupported` instead of a clean release. The suite is green, so none currently do; the trap is for the next test author.

**S8 — SMELL — `ResourceFlightUnsupported` is classified `Class::Config`, and the history vocabulary widening is a one-way door.**
`crates/bridge-core/src/execution_policy.rs:630-632` maps it to `(Class::Config, "bridge.resource_flight_unsupported")` and `error.rs:188-192` to `RejectRequest`. The category is static and leaks nothing (correct for the wire), but `Config` tells an operator to check their configuration for what is by construction an internal defect — a decorator that failed to forward. Separately, `workflow_history.rs:527-536` widening the persisted vocabulary is additive for writers but not for readers: an older binary validating a row containing `"retained"` will reject it. Worth one line in the compat ledger.

**S9 — SMELL — `attach_resource_flight_owner_v1` has zero production callers, and its `AcpBackend` implementation is only self-consistent by accident.**
The only non-test occurrence outside the impls is `WorktreeBackend`'s own forwarding body (`crates/bridge-worktree/src/backend.rs:2751-2756`). Inside `AcpBackend`, `attach_process_flight_owner` returns `Ok(())` when `supervised` is `None` (`acp_backend.rs:4605-4613`, `if let Some(...)` with no `else`), i.e. attachment silently "succeeds" against nothing; the caller is saved only because `attach_resource_flight_owner_v1` then re-reads `resource_flight_v1()` (`:7043-7048`), which refuses in that same state. That ordering is load-bearing and undocumented. Since this is the only trait pass, 3c1/3c2 will build on it — worth an `else { Err(ResourceFlightUnsupported) }` or a comment pinning why the re-read is required.

**7. Real-host closure test — PASS, genuinely discriminating.**
`crates/bridge-core/src/process.rs:3072-3200`. Real descendants (`/bin/sh` root with `trap '' TERM`, spawning a subshell that also traps TERM and `exec sleep 300`), so a TERM-only implementation fails the liveness assertions. Readiness is a real stdout pipe handshake with both PIDs cross-checked against `process.pid()` — no sleep race. Zero-grace closure, then the assertions read the **journal**, not exit status: `SIGSTOP` before `SIGKILL` for each PID independently, and `kill_descendant < kill_root` for child-first order. The no-leak proof is bounded polling of `proc_state` (new `/proc/<pid>/stat` reader on Linux, `ps` elsewhere) with a 2s timeout, accepting zombie as not-live — reasonable. Wiring is production-shaped in construction (real `FileResourceFlightJournal`, `ResourceFlightRegistryV1`, `ResourceFlightOwnerV1`, `DurableProcessFlightV3`) but is not yet reached *through* `AcpBackend`: the production V3 spawn at `acp_backend.rs:3391-3402` is conditional on `process_flight.is_some()`, which slice 4 arms. Two caveats to carry, neither a defect: the `_host_signal_semantics` suffix excludes it from the hermetic suite, so it survives only as an explicitly-selected single test (handoff §7 records exactly that, 1 passed), and the V3 route stays unexercised end to end until slice 4.

The frozen custody transition table `LEGAL_CUSTODY_TRANSITIONS_V1` (`crates/bridge-worktree/src/custody.rs:387-405`, 10 edges) gains no edges — `custody.rs`, `custody_writer.rs` and `fs_custody.rs` do not appear in the diffstat at all. ## Ship rationale

The slice does the hard thing correctly: the authority gate sits before effects at every funnel I could reach, the refusing default is genuinely load-bearing and its negative test discriminates rather than tautologizing, and the disposition survives the production chain into terminal history. The residual risk is concentrated in one place worth acting on before 3c1 — the `Preserved > Retained` lattice (S1), which is cheap to change now and expensive after `ContainerRwBackend` starts returning `Retained`. Everything else is latent, fail-closed, or pre-existing. Ledger for the next slice: S1 (ordering, or split into two fields), S2 (durable inner re-derivation), S3+S4 (close the two projection sites before `workflow_owner` goes live), S5 (log registry refusals), S9 (make `attach`'s `None` branch explicit).
