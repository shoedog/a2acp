## Findings

### W1 — WRONG: per-session owner rows exhaust the V2 in-memory flight journal, then every new session on that agent fails permanently
`crates/bridge-acp/src/acp_backend.rs:4666` `session_entry` → `:4673` `self.attach_process_flight_owner(key)?` → `:4570` `attach_process_flight_owner`. This is **unconditional** — it is not gated on `is_legacy_v2()`, so it runs on today's production V2 path (`process_flight_route_v3` is `None` everywhere). `:4615` `detach_process_flight_owner` is called from `release_session_result` (`:5525`).

Mechanism: `crates/bridge-core/src/process.rs:1976` gives every V2 generation an `InMemoryResourceFlightJournal::new(512)`. `retained_resource_flight.rs:1040` `attach_owner` appends an `OwnerAttached` row per new owner; `:1063` `detach_owner` appends `OwnerDetached`. `retained_resource_flight.rs:400` `InMemoryResourceFlightJournal::append` → `:320` `admission_check`, where `needed = records.len() + 1 + slots_after`; `needed > cap` returns `ResourceFlightJournalError::Full`. There is no eviction — only `rows.push`.

Failure scenario: a warm `serve` with one ACP agent backend multiplexing bridge sessions (the code states this at `acp_backend.rs:5561`). Spawn writes 3 rows (`FlightReserved`, `OwnerAttached` for the spawn owner, `ProcessTreeCaptured`). Each new `SessionId` adds 1 row; each `release_session` adds 1 more. At the 510th row, `attach_owner` returns `Full` → `ProcessAuthorityErrorV1::Flight` → `BridgeError::agent_crashed("ACP process-flight owner attachment failed")` → `session_entry` returns `Err` → every subsequent `prompt`, `ensure_session`, `cancel_inner`, and `reconcile_session` on that agent fails forever with an error unrelated to the request. That is ~509 distinct sessions, or ~254 open/close cycles, on a single long-lived backend. Nothing recovers it short of respawning the agent. No test exercises more than a couple of attach/detach cycles.

### W2 — WRONG: the containment refusal path leaves the whole tree SIGSTOPped and unkillable
`crates/bridge-core/src/process.rs:1511` `close_and_kill`; `:1065` `process_is_stopped`. `grep -rn SIGCONT crates bin` returns **zero matches** — nothing ever resumes a stopped member.

Failure scenario: the root handles SIGTERM slowly (or ignores it) and one of its children exits during the grace window, becoming an unreaped zombie inside the group. `close_and_kill` SIGSTOPs every member (`kill` on a zombie returns 0, recorded as a normal stop). `process_is_stopped` for the zombie reads Linux `/proc/<pid>/stat` state `'Z'` (`:1071`) or darwin `pbi_status == SZOMB` (`:1110`) → `false`. The zombie's parent is now itself SIGSTOPped, so it can *never* reap it: the probe stays false for all 16 iterations → `ContainmentUnstable` (`:1543`). **No SIGKILL is issued to any member.** `terminate_blocking_inner:1710` records the error, `settle_dispatch` settles `Failed`, and the flight is terminal — a later `terminate` claims `Finished` and only joins (`:1665`), so no retry exists. Net: the agent tree is frozen and unkillable through the bridge — strictly worse than the V2 group SIGKILL it replaces and worse than doing nothing. Same class: any member in Linux `D` state during the volley.

Bounded fix: treat a member whose probe reports exited/zombie as contained (it cannot fork), and SIGCONT every member the volley stopped on every refusal exit.

Latency note: V3 is not yet reachable in production, so this is latent — but it is the slice's central mechanism and the acceptance item I was asked to verify.

### S1 — SMELL: no real-host coverage of the V3 containment closure
Every V3 test uses `FakeProcessAuthority` with `child: Mutex::new(None)` (`process.rs:3050`). `platform_stopped_state_probe_observes_sigstop_host_signal_semantics` (`:3532`) spawns via `OwnedProcessTreeV1::spawn`, which is `ProcessFlightProvisionV1::LegacyV2` (`:1912`) — its `terminate` runs `terminate_blocking_legacy_v2`, not the V3 closure. SIGSTOP-verify → child-first SIGKILL has never executed against real syscalls with a real child and real descendants.

### S2 — SMELL: the forced-kill-failure test's disposition assertion is non-discriminating
`process.rs:3284` `forced_failing_kill_is_typed_and_journaled` asserts `result.disposition == Failed`. Because every fake-authority V3 terminate has `child == None`, `terminate_blocking_inner:1708` sets `authority_error = ProcessUnavailable` and `settle_dispatch:1563` yields `Failed` regardless of the injected EPERM. Only the journal-row assertion actually discriminates.

### S3 — SMELL: awaited `escalate_terminate` delays the turn kill-switch
`acp_backend.rs:5572` became `async` and is awaited at `:5279`, `:6539`, `:6589`, `:6624`. The kill-switch notify at `:5280` now fires only *after* terminate settles, so a hung turn's stream unblocks up to `TERMINATE_GRACE` + `BLOCKING_TERMINATE_REAP_BOUND` (≈0.5–5.5 s) later than before. Bounded, no hang — a latency regression on the exact path the kill switch exists to make prompt.

### S4 — SMELL: `join_blocking` has no timeout and `finish_action` is not drop-guarded
`process.rs:1294` Condvar-waits while another thread holds `Driving`. A panic in the driver between `claim_action` (`:1268`) and `finish_action` (`:1283`) strands every joiner forever, contradicting the "no eternal-hang window" claim. For V3 this is reachable from `AcpBackend::drop` (`acp_backend.rs:7386`) — a blocking Condvar wait inside `Drop` on a Tokio worker thread.

### S5 — SMELL: `read_only_controller` is write-only
`process.rs:1221` / `:2151`, bound at `acp_backend.rs:3426`, never read anywhere. Dead state.

### S6 — SMELL: real-host V2 drop coverage moved to the private seam
`process.rs:2729` `drop_group_kills_descendants_host_signal_semantics` uses `Supervised::spawn` (`drop_signal = true`, `#[cfg(test)]`-only Drop at `:639`), so it no longer exercises production V2 drop (`legacy_v2_drop`, `:1759`), which is pinned only by the fake-authority test at `:3309`. Mechanism is equivalent (same `kill(-pgid, SIGKILL)`), so this is coverage, not behavior.

### S7 — SMELL: V2 drop is now conditional on the action claim
`process.rs:1760`: if the action mutex is poisoned, `legacy_v2_drop` returns `Err` and issues **no** group SIGKILL; the pre-change `Supervised::drop` was unconditional. `kill_on_drop` still reaps the direct child, but descendants would leak.

### S8 — SMELL: `LIFECYCLE_SLOTS` 3→4 leaves a permanently unconsumed slot
`retained_resource_flight.rs:44` / `:1122`. Changes the value written into every new `IntentJournaled.reserved_lifecycle_slots`, and flights with no `GuardTransferred` end with one reserved slot never consumed. No production cap risk (all journals are 512) and nothing pins the value.

### Ledger clarification (extends item (a) — the mechanism differs from the ledger's description)
The darwin red is **deterministic**, not intermittent: 10/10 failures running it alone. Root cause is not "the ImmutableStart row lacks `pid: Some(_)`". `process.rs:3471` spawns `"/bin/true"`, which **does not exist on macOS** (only `/usr/bin/true`; `ls /bin/true` → No such file). The bind half therefore fails at `ProcessBindingStageV1::Spawn` and never reaches `ImmutableStart`; `assert_eq!(bind_error.kind(), NotFound)` at `:3482` passes for the wrong reason (ENOENT, not the fake authority's NotFound). The production code at `:2044`–`:2066` unconditionally passes `Some(pid)` and is correct — the repair is the test's binary path, not the production path. (`bin/a2a-bridge/src/main.rs:11672/11726/11735` also hardcode `/bin/true` but never spawn it.)

## Invariant verdicts

Loud (error trace + `Settled{Failed}`), and it is the stated capability-gating trade, but it means any V3 backend dropped without `retire()` leaks its whole tree. Confirm this is the intended slice-4 contract.
